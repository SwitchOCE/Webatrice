## How to use this matrix

Each stable ID is a planning unit, not necessarily one pull request. `Complete` means the material capability is available; it does not imply pixel or interaction identity. `Partial` means a usable or lower-layer implementation exists but important behavior is absent. `Missing` requires negative searches across plausible UI, state, protocol and test paths. `Divergent` is a material behavioral difference; browser-native differences that preserve the complete outcome are documented without being scored as gaps. `Unverified` is intentionally used where evidence cannot support a stronger classification.

Priorities are impact-first: `P0` blocks core connection/deck/gameplay use; `P1` is a major normal workflow; `P2` is secondary or a substantial UI/UX deficiency; `P3` is specialized, administrative, desktop-specific or low-impact. A priority is not an effort estimate.

Evidence is repository-relative to the matching baseline. “Static” means source inspection; “test-defined” means an existing automated test establishes intended behavior. The audit's own executed validation is summarized in [current state](current-state.md#verified-build-and-test-status): all unit, integration, and Docker/Servatrice e2e suites passed. Runtime confidence applies only to the eight scenarios listed below; row notes such as “not runtime observed” remain valid for capability outside those scenarios. See [limitations](audit-limitations.md) before generalizing a passing smoke path.

## Snapshot

The audit contains **94** stable planning items: **29 Complete**, **35 Partial**, **22 Missing**, **6 Divergent**, and **2 Unverified**. Priorities are **23 P1**, **25 P2**, and **46 P3**; no P0 blocker was established at these commits. Absence of a P0 classification does not mean the client has full parity—it means the audited gaps did not block the already working core connection, deck submission, game creation, or gameplay paths.

## Recommended planning order

1. Resolve any `P0` deck/gameplay blockers and restore reliable connection/session recovery.
2. Finish the visible protocol-backed `P1` workflows: account maintenance, server/room/chat failure feedback, server notices, deck persistence/validation, replay list/playback, and core game actions.
3. Add browser-quality gates: Webatrice lint in CI, Chromium/Firefox/WebKit smoke coverage, error boundaries, accessibility checks, and reconnect e2e.
4. Complete secondary parity and consolidate the large revamp components without changing their functional contract.
5. Implement sensitive staff/admin workflows only after role, privacy, confirmation and audit requirements are explicit.

UI/UX improvements should ship with the relevant parity row: visible disabled reasons, keyboard alternatives to drag/right-click, preserved failed drafts, progressive loading/error states, and web-native storage/update/notification outcomes. They should not displace missing capability of comparable impact.
