# Task t1: PR T1, unit-suite memory (test infrastructure)
Push branch: `claude/parity-t1-test-memory`. PR file: `parity-t1-test-memory`. Base: `origin/claude/parity-31-deck-i18n-a11y` (87a20ef, the largest suite so far, ~3.8k webatrice tests).

Problem: the webatrice unit suite (`vitest run --maxWorkers=2`) peaks around 9 GB RSS at 2.3k tests, and now OOMs a 13.6 GB container at ~3.8k tests, so workers have to split the run. CI (GitHub's public-repo Linux runners have 16 GB) will start failing soon. Measured numbers are in `/tmp/notes/prs/parity-25a-platform-prefs.md` (the memory section).

1. **Measure** per-file heap growth (`--logHeapUsage`, `--pool` / `--isolate` variants, `--maxWorkers=1`), find the top offenders, and attribute the cause. Usual suspects:
   - store or module singletons not reset between files;
   - un-cleaned timers, listeners or `ResizeObserver`/`MatchMedia` stubs;
   - jsdom documents kept alive;
   - large fixtures (card DBs, protobuf descriptors) re-imported per file;
   - Dexie / fake-indexeddb instances not closed;
   - React roots not unmounted;
   - MUI emotion caches.
2. **Fix the root causes** in test setup and fixtures, and in product code if a real leak shows up (then add a spec). Tune the vitest config (pool, isolate, `poolOptions` memory limits) only on top of real fixes, never instead of them.
3. **Target:** the whole webatrice unit suite in one `npm test` with peak RSS < 4 GB at `--maxWorkers=2`, and no slower than today ±10%. Report before/after numbers (peak RSS, wall time) in the PR file.
4. Add a CI guard if it's cheap, e.g. a `--maxWorkers=2` run under `ulimit -v`, or a script that fails over a memory budget.

Gate: the full gate, with every package's unit suite run as **one command**. e2e only if product code changed.
