## 0. Cross-cutting findings that shape the PR

1. **Webatrice has no "Game" menu.** Desktop's `TabGame::createMenuItems` (`D/interface/widgets/tabs/tab_game.cpp:1042-1119`) holds,
   in order:
   - the Phases submenu (11 phases, sep, "Next &phase", "Next phase with &action");
   - "Next &turn", "Reverse turn order", sep;
   - "&Remove all local arrows", "Rotate View Cl&ockwise", "Rotate View Co&unterclockwise", sep;
   - Game info …

   Desktop never disables these items. The server gates them. GAME-028/029/030 all need a home. **Decision:** add a
   compact `GameMenu` (MUI `Menu` on a button) to `W/components/BattlefieldSidebar/BattlefieldSidebar.tsx`, next to
   Leave / Concede (`:583-650`; the comment at `:608-610` already anticipates more buttons). Items are gated by
   `useGameAffordances`. It is a game-level component, so Phase 7/8 do not touch it.
2. **Seat menus are still inline in PlayerBox:**
   - battlefield `battlefieldMenuItems` (`PB:4206`) and `opponentBattlefieldMenuItems` (`PB:4391`);
   - library pile (`PB:3956`), library CardBackZone (`PB:5461`), hand zone (`PB:3986-4075`);
   - the opponent-card "View related cards" placeholder (`PB:6683-6687`).

   Phase 7 moves those regions into `PlayerInfoPanel` / `HandZone` / `ZoneStack` / `Battlefield`. **Every PR 17 menu
   change goes into a pure model file under `W/components/context-menus/`, never into PlayerBox JSX.** That way the
   Phase 7 move carries the items instead of conflicting with them. See §14.
3. **Shortcut mechanics.** Adding a shortcut touches four places:
   - `SC/types.ts` `ActionId`;
   - `SC/defaults.ts` (`KeyboardEvent.code` syntax; browser-reserved keys are remapped);
   - `SC/SettingsTab/ShortcutsTab.i18n.json` `ShortcutsTab.action.<id>`;
   - a handler: `useShortcut` in `W/hooks/useGameShortcuts.ts` for game-level actions, or `SEAT_SHORTCUT_ACTIONS`
     (`W/components/ui/SeatShortcutsContext.tsx:15-61`) plus the seat's published op (`PB:1666ff`,
     `usePublishSeatShortcuts` at `PB:2255`) for seat actions.

   Menu hints come from `useShortcutHints()` (`SC/useShortcutHints.ts:22-33`), passed as `shortcutHints` into
   `cardContextMenu.model.ts` (`:30`).
4. **Legacy "reveal to all" bug (new finding).** `Command_RevealCards.player_id` is proto2 `optional sint32 [default = -1]`.
   `Server_AbstractPlayer::cmdRevealCards` (`NET/server_abstract_player.cpp:1485-1490`) returns `RespNameNotFound` when
   `has_player_id()` and no player has that id. "All players" must therefore **omit** `player_id`.
   - The seat port does this correctly (`W/components/ui/GameBoardCell/usePlayerZoneCommands.ts:39-56`).
   - The legacy game-level path sends an explicit `playerId: -1`:
     - `W/dialogs/RevealCardsDialog/useRevealCardsDialog.ts:23,51-61`;
     - `W/components/context-menus/ZoneContextMenu/useZoneContextMenu.ts:66-70`;
     - the senders in `hooks/dialogs/use{Hand,Zone,Library}DialogActions.ts`.
   - The `webatrice-game.instructions.md` "Dialog parity" bullet (`targetPlayerId === -1` means all players) documents
     the UI convention, not the wire.
   - **Unverified:** whether protobuf-es serialises an explicitly set default. Proto2 fields have explicit presence, so
     it should.
   - Add an integration wire test first. If it fails as predicted, fix it in this PR (S) or hand it to Phase 8, which
     retires these legacy menus anyway. Include it here because "Reveal to…" shares the code.
5. **Say macros depend on `origin/parity/19-settings` (`e3a1137`).** `useMessageMacros()` (in `src/hooks/useSettings.ts:66-72`
   there, pref `messageMacros: string[]`, default `[]`) is not on the seat branch or on master. Root `hooks` is importable
   from features (`eslint.boundaries.mjs:63-64`). Merge or rebase onto 19 before the Say commit, or put that commit last.
6. The e2e fixture `packages/webatrice/e2e/fixtures/test.ts` does not exist on this base. Import `test` from it once the
   e2e-hardening branch is in the base; until then, use the existing `e2e/specs/*` pattern.

## 1. GAME-028 — Next phase with action (S)

**Desktop**
- `TabGame::actNextPhaseAction` (`tab_game.cpp:675-689`) computes `phase = (currentPhase + 1) % 11`.
  - If `phase == 0`: emits `turnAdvanced` → `Command_NextTurn {}` (`game_event_handler.cpp:177-180`).
  - Otherwise: `Command_SetActivePhase { phase }` (ext 1023, `uint32 phase = 1`).
  - Then `phasesToolbar->triggerPhaseAction(phase)` (`D/game_graphics/phases_toolbar.cpp:245-250`) runs that phase's
    double-click action:
    - phase 0 → `actUntapAll`: `Command_SetCardAttr { zone: "table", attribute: AttrTapped, attr_value: "0" }`,
      card_id unset;
    - phase 2 → `actDrawCard`: `Command_DrawCards { number: 1 }`;
    - other phases: no extra command.
  - So End → (wrap) sends NextTurn and then untaps the **local** player's table. Upkeep → sends SetActivePhase(2) and
    DrawCards(1).
- Label "Next phase with &action". Shortcut `Player/aNextPhaseAction` = **Shift+Tab**, group Game_Phases
  (`shortcuts_settings.h:497`).
- No client gate. The server rejects SetActivePhase from a non-active non-judge (`NET/server_player.cpp:558-579`), but the
  draw and untap still go through. **Webatrice decision:** gate on `canAdvancePhase`, or on `canPassTurn` for the wrap.
  This is stricter than desktop and avoids a half-applied action. Note it in the PR.

**Protocol:** all builders exist:
- `setActivePhase` (`SOCK/commands/game/setActivePhase.ts`), `nextTurn`, `drawCards`, `setCardAttr`;
- reducers `activePhaseSet` and the turn reducers exist.

**Webatrice now**
- `W/components/PhaseTrack/usePhaseBar.ts:20-87` already has `handlePhaseClick` (optimistic `activePhaseSet` plus
  rollback), `handlePass`, `handleUntapAll` (`setCardAttr` TABLE, cardId -1, AttrTapped "0") and `handleDrawOne`.
- `useGameShortcuts.ts:130-150` duplicates the next-phase logic (`PHASE_COUNT` at `:15`).
- `game.prevPhase` (Webatrice-only, no desktop equivalent) owns **Shift+Tab** (`SC/defaults.ts:21`).

**Landing**
- Extract a pure `nextPhaseActionPlan(currentPhase): { advance: 'nextTurn' | { phase }, then: 'untapAll' | 'drawOne' | null }`
  into `W/components/PhaseTrack/phaseActions.ts`.
- Add `useNextPhaseAction()` in the same directory. It reuses `usePhaseBar`'s handlers; `useGameShortcuts` and the game
  menu both call it.
- Have `useGameShortcuts` `game.nextPhase` call the same plan, which removes the duplicate.
- New `ActionId 'game.nextPhaseAction'` with default `['Shift+Tab']`. **Move `game.prevPhase` to no default** (still
  rebindable) and note it in the changeset. Desktop wins on its own key.

**Deviation to flag, out of scope:** a single click on Untap in `PhaseTrack.tsx:218` always untaps. Desktop
(`phases_toolbar.cpp:252-263`) runs the action only when the button is already active. Record it as a follow-up and do
not fix it in PR 17. PhaseTrack labels are hard-coded English (`:50-89`, `:273-275`); also a follow-up.

**Tests**
- `phaseActions.spec.ts`: a table over 0..10.
- `useNextPhaseAction.spec.tsx`: wire order. Wrap gives `nextTurn` then `setCardAttr`; phase 1→2 gives `setActivePhase(2)`
  then `drawCards(1)`; gating.
- `Game.shortcuts.spec`: Shift+Tab fires the action, and prevPhase is unbound.
- Integration (`integration/src/features/game/`): optional. The round trip is covered by the existing phase specs.

## 2. GAME-029 — Reverse turn order (S)

**Desktop**
- `aReverseTurn` → `Command_ReverseTurn {}` (ext 1034, `game_event_handler.cpp:182-185`). Label "Reverse turn order"
  (`tab_game.cpp:336`). No confirmation.
- `getShortcut("Player/aReverseTurn")` exists, but **there is no entry in `shortcuts_settings.h`**, so it has no default
  and does not appear in the settings.
- Server (`NET/server_abstract_participant.cpp:407-428`, `server_player.cpp:597-604`): game started; non-judge spectator →
  FunctionNotAllowed; conceded non-judge → ContextError. It then toggles and broadcasts `Event_ReverseTurn { reversed }`
  with the actor's player id.
- Log: "%1 reversed turn order, now it's %2." with "reversed" / "normal" (`message_log_widget.cpp:577-582`).
- No persistent indicator.

**Protocol (all exist)**
- `reverseTurn(gameId)` (`SOCK/commands/game/reverseTurn.ts`).
- The event `SOCK/events/game/reverseTurn.ts` → `GameResponseImpl.turnReversed` (`DATA/api/GameResponseImpl.ts:144`) →
  `game.reversed` (`DATA/store/games/game.reducer.turn.ts:32-38`).
- Selector `isReversed` (`game.selectors.ts:226`). Log formatter `formatTurnReversed` (`messageLog.ts:652`).

**Bug (fix in this PR, S):** the log line names `preGame.activePlayerId` (`game.listeners.ts:995-1010`), not the actor.
`meta.playerId` is dropped at `SOCK/events/game/reverseTurn.ts:6`.
- Pass `playerId` through `turnReversed(gameId, reversed, playerId?)`. The new parameter is optional (additive).
- Changesets: sockatrice patch, datatrice patch.

**Landing**
- A game menu item "Reverse turn order", gated on `useGameAffordances().canPassTurn`. That matches
  `webatrice-game.instructions.md` "Phase model": `canPassTurn` drives `cmdReverseTurn`.
- `ActionId 'game.reverseTurn'` with `sequences: []`, so it is rebindable. That is a small extension over desktop; say so.
- No direction indicator, because desktop has none. Optionally show "(reversed)" in the game menu label from `isReversed`.
  Default: no.

**Tests**
- Game menu spec: the item sends one `reverseTurn` and is disabled for a spectator or a conceded player.
- `reverseTurn` event spec: playerId reaches the response.
- Listener/messageLog spec: the actor's name is used.
- Integration `websocket/game.spec.ts`: Event_ReverseTurn with player_id gives the right log line.

## 3. GAME-030 — Rotate view CW/CCW (S-M)

**Desktop**
- `actRotateViewCW` → `scene->adjustPlayerRotation(-1)`; CCW → `+1` (`tab_game.cpp:699-707`).
- `GameScene::rearrange` (`D/game_graphics/game_scene.cpp:263-361`) collects the non-conceded players. `firstPlayerIndex`

- Local only: no command, not persisted, available to spectators.
- Shortcuts `Player/aRotateViewCW` / `Player/aRotateViewCCW` have **no default** (`shortcuts_settings.h:730,733`).

**Webatrice now**

  spectators (`:92-94`); the rotation is at `:95-98`. There is no offset.
- `MIN_PLAYERS_FOR_TWO_COLUMNS = 4` is hard-coded (`:33`); desktop makes it a setting. Not in scope.

**Landing**
- `useGameBoardLayout(game, rotation = 0)` with start = `mod((max(localIndex, 0)) + rotation, n)`.
- `rotation` is `useState` in `useGame` (per game, ephemeral, reset on unmount). Expose `rotateView(+1 | -1)` on the
  game context.
- Do not use Redux or localStorage, because desktop does not persist it.
- Two game menu items, plus `ActionId 'game.rotateViewCW'` / `'game.rotateViewCCW'` with `sequences: []`, registered with
  `useShortcut` in `useGameShortcuts` (spectators allowed: `hasLiveGame`, not `inGame`).
- Arrows: `GameArrowOverlay` reads DOM positions, so it follows automatically. Check that it re-measures on a layout
  change.

**Tests**

  order.
- `Game` spec: rotating moves seat cells and sends no request.
- An e2e is not needed.

## 4. GAME-021 — Open game deck in editor (M)

**Desktop**
- Library menu, local or judge only, after a separator: "&Open deck in deck editor" (`library_menu.cpp:48,203-205,224`).
  It is disabled until `deckChanged` (`:84-89`) and then never disabled again. No shortcut, no confirmation.
- `PlayerActions::actOpenDeckInDeckEditor` (`player_actions.cpp:219-222`) opens `player->getDeck()` (the DeckList from
  `ServerInfo_Player.deck_list`) as a **new unsaved editor tab** (`tab_supervisor.cpp:989-999`). There is no lookup.
- The `.cod` keeps setShortName, collectorNumber and uuid per card.

**Webatrice now**
- `W/components/ui/GameBoardCell/useOpenDeckInEditor.ts:45-89`:
  1. reads `player.deckList` (`DATA/store/games/game.reducer.helpers.ts:106`);
  2. keeps only the parsed name (`:62-72`);
  3. lower-case matches it against `flattenBackendDecks(getBackendDecks)` (`:74-81`);
  4. navigates to `/deck/:deckId`.

  This fails on file- or clipboard-loaded decks (the item is disabled), on duplicate names (the wrong deck opens), and on
  stored copies edited after the game loaded them (stale contents).
- `parseCod` / `serializeCod` (`services/decks/cockatriceDeckDocument.ts:241-310`) round-trip the printing fields, so data
  loss is not the problem. The lookup is.
- The editor (`features/decks/useDeckEditor.ts:122-213`, `DeckEditor.tsx:102`) opens server-stored decks only (deckDownload
  by id).
- Feature→feature imports are lint errors, so the handoff has to go through a route, `services` or `store`.

**Decision (recommended): true parity through an unsaved-deck handoff (option b).**
- Add a root service `services/decks/deckHandoff.ts`: `stageDeckDocument(cod: string): string` returns a token and keeps
  the text in an in-memory Map; `takeStagedDeck(token)` reads it once.
  - It lives in `services`, which both features may import.
  - It holds no Redux state, because a large XML string does not belong in the store.
- Add route `RouteEnum.DECK_DRAFT` = `/deck/draft/:token`.
- `useDeckEditor` gains a draft source: it hydrates from `takeStagedDeck(token)` with `deckId = undefined`, so the first
  save goes through `deckUpload('', 0, xml)` like the "new deck" flow in `Decks.tsx:181-220`.
- `useOpenDeckInEditor` becomes: if `deckList !== ''` and the user is local or judge, return
  `() => navigate(deckDraft(stageDeckDocument(deckList)))`.
  - Drop the backend-deck fetch.
  - Gating now matches desktop (enabled once a deck is known).
- Rejected option (a): uploading as a new stored deck and opening it creates server-side decks that desktop never creates.

**Tests**
- `deckHandoff.spec.ts`: single read, unknown token.
- `useOpenDeckInEditor.spec.tsx`: no `deckList` → undefined; a deck that is not on the server still opens; duplicate stored
  names do not matter.
- `useDeckEditor.spec`: the draft source hydrates every printing field, and the first save uploads with no id.
- Integration `features/decks.spec.tsx`: the game → editor route round trip preserves `setShortName` / `collectorNumber` /
  `uuid`.
- Size **M**. It touches features/decks; check with the deck-editor branches (GAME-004/005/006) for conflicts in
  `useDeckEditor`.

## 6. GAME-027 — Tally (M)

**Desktop (master only; absent from 3.0.0: #7021 / #7057 / #7252)**
- `TallyMenu` (`D/game_graphics/player/menu/tally_menu.cpp`): "Tally" with exclusive checkable items "None", a separator,
  then "Subtypes", "Total Power", "Total Toughness". It is on **every** player's menu, opponents included
  (`player_menu.cpp:48`). No shortcuts.
- The choice is only persisted as the local setting `interface/tallyType`. No command, no chat.
- Output is an overlay at the bottom-right of `GameView` (`game_view.cpp:206-320`), recomputed on selection or setting
  change over **all selected cards in any zone or seat**. Rows sit above the "N selected" count label (shown at ≥2 when
  `showTotalSelectionCount` is on).
- Computations (`D/game_graphics/tally/`):
  - Subtypes:
    - skip face-down or nameless cards;
    - type line split on " // " and then on " — ";
    - count each subtype word;
    - sort by count ascending, then name.
  - Power / Toughness:
    - no rows unless some card has a live PT;
    - sum `max(0, int)` of P or T from the live `getPT()`, with non-numeric counting as 0.

**Protocol:** none. `DATA` cards carry the live `pt` and `faceDown`. The type line comes from the catalog
(`services/cards/cardCatalog.ts:37-48`, `lookupCardsCached(names)` at `:195`, with `faces[].typeLine` for multi-face cards).

**Landing**
- `W/utils/tally.ts`: pure `computeTally(cards, type, typeLineOf)`.
- `W/hooks/useSelectionTally.ts`: resolves `useGameSelection().selectedCardKeys` against the datatrice cards plus a
  catalog lookup.
- `W/components/TallyOverlay/TallyOverlay.tsx`: a game-level overlay inside the board container. Phase 7 does not touch it.
- Setting: a local preference `tallyType: 'none' | 'subtypes' | 'power' | 'toughness'`.
  - Use 19-settings' `usePreference` if that branch is in the base.
  - Otherwise use the localStorage singleton pattern of `W/hooks/usePhaseTrackPinned.ts:30-45`.
- Menu: a radio submenu `buildTallyMenu(current, onSet)` in `playerMenu.model.ts`, on both own and opponent battlefield
  menus (`PB:4206`, `PB:4391`).
- Optional: the "N selected" count label. Desktop gates it behind a setting. **Default: include it, always on at ≥2.**
  Keep it a separate commit so it can be dropped.
- Version gate: none, because tally is client-only. Mention in the PR that it mirrors 3.1 master.

**Tests**
- `tally.spec.ts`, as a table:
  - DFC " // "; em dash; face-down skipped;
  - `*` and `X` P/T count as 0; negative counts as 0;
  - no-PT → no rows;
  - sort order.
- `useSelectionTally.spec.tsx`: cross-seat selection, catalog mocked.
- `TallyOverlay.spec.tsx`: hidden when there are no rows.
- Menu model spec: the radio state.
- Size **M**.

**(ii) The P/T sort leaves non-creatures unsorted**
- In `W/dialogs/ZoneViewDialog/zoneViewSort.ts:185-195`, `ptSortKey(null) = +Infinity`, and `Infinity − Infinity = NaN`,
  which is not 0. The comparator returns NaN, so the name tie-break never runs.

  database P/T string `rightJustified(10,'0')`, then by name, then by printing. Non-creatures ("" → "0000000000") come
  **first**; `*` sorts before digits; the order is lexicographic ("2/10" sorts after "3/3").
- **Decision:** fix the NaN (`const dp = ka === kb ? 0 : ka - kb`, the same for toughness) and add the name and
  scryfallId tie-breaks. **Keep** numeric ordering and non-creatures last. Desktop's string ordering is an artefact
  ("2/10" after "3/3"), not a rule worth copying. Note the deliberate deviation in a code comment and in the PR.
